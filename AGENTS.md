# VWARD — инструкции для Codex

Этот файл задаёт короткие правила входа в проект. Актуальные решения, технические доказательства и история находятся в репозитории; не заменяй их предположениями.

## Начало задачи

1. Проверь текущие ветку, HEAD, базовый PR и формулировку поручения. Продолжай с последнего зафиксированного коммита; не начинай повторный полный аудит.
2. Прочитай обязательные правила `docs/AGENT.md` и относящиеся к задаче разделы `docs/ROADMAP.md`. Для маршрутизации используй `docs/ROUTING_B_IMPLEMENTATION.md`, `docs/ROUTING_AUDIT_CONTRACT.md` и `docs/RS6_READ_ADAPTERS.md`; для P-7 — `docs/P7_B_INTEGRATION_2026-10-31.md`.
3. Работай с реальными файлами и вызовами на выбранном HEAD. Исторический отчёт, старый скриншот или прежний CI не доказывают текущее состояние роутера.
4. Перед большим пакетом кратко предложи самую экономичную **доступную** модель и уровень рассуждений. Не выдумывай наличие моделей, не переключай их без нужды.

## Правила разработки

- Один исполнитель изменяет одну рабочую ветку за раз. Codex и Claude Code работают **поочерёдно**, принимая работу через GitHub. Изменения — в отдельных ветках и черновиках PR; не перезаписывай чужой незавершённый прогресс.
- Работу пакета выполняет **один доступный агент**; второй её не дублирует и не повторяет завершённые этапы. Независимый аудит другим агентом — **адресный**, только для действительно рискованных изменений (запись в маршрутизацию, переключение DNS, восстановление после сбоев), а не обязательный шаг перед каждым этапом.
- Сначала воспроизведи подтверждённую ошибку тестом, затем внеси минимальный фикс и проверь вызовы, совместимость POSIX sh / BusyBox / Entware, контрольные суммы и откат.
- Не ослабляй тесты, ownership, admission/update barrier, Ed25519, SHA-256, защиту DNS/AGH, резервирование и recovery ради зелёного статуса.
- Чужая или неизвестная FQDN-группа — только наблюдение без права изменения. Название, номер списка, похожие домены и legacy-запись не доказывают владение.
- Сохраняй пользовательские настройки, маршруты и данные возврата. При неполном или изменившемся снимке — `unknown`; при неподтверждённом результате записи — явная ошибка, приватный recovery и запрет опасного повтора.
- Архитектура B: использовать существующие механизмы, не добавлять демон/таймер/опрос без доказанной необходимости. Текущий RS-6 — **audit/dry-run**: никакого подключения writer и реального изменения маршрутов/DNS до отдельного согласования безопасности.
- Сохраняй **Панель VWARD** полностью, включая мобильный вид; не заменяй её сокращённым макетом. Три источника маршрутизации в будущем — три отдельных стандартных тумблера.
- Тесты сначала точечные; полный CI — на изменённом конечном code HEAD. Уже успешные длительные проверки не повторяй. Всегда различай локальный fixture, штатный CI и реальную приёмку Keenetic.

## Запреты и передача работы

**Без отдельной команды владельца «Выпускаем» запрещено** сливать PR в `dev`/`main`, менять публикационную VERSION, подписывать/публиковать релиз, менять feed или устанавливать обновление. Изменения конфигурации Keenetic, VPN и AGH требуют отдельного явного разрешения; отсутствие доступа к роутеру — не повод их имитировать как успешно принятые.

Команды для Termius — только по `docs/termius-standard.md`; секреты, URL подписок и приватные данные в GitHub не переносить.

В конце пакета зафиксируй HEAD/PR, изменения, точные PASS/FAIL/SKIP, открытые риски и следующий шаг в принятой документации. В чат — краткий отчёт до 15 строк. Перед новой задачей, передачей другому агенту или заполнением контекста начинай новую сессию с GitHub HEAD; новая сессия **не** сбрасывает лимиты использования.
