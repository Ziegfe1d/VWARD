# Аудит ресурсов 0.2.0-rc.1

Аудит измерял потребление ресурсов VWARD на роутере:
- процессы;
- процессор (CPU);
- память (RAM);
- запись на USB-накопитель;
- нагрузку от Console.

Функции не менялись: исправлены только расход ресурсов и найденные дефекты надёжности.

## Как измерялось

Реального роутера в CI нет, поэтому собран **эмулятор роутера**
(`tests/perf/emulator/build-rootfs.sh`). Это chroot из четырёх частей:
- **Userland Entware.** BusyBox, jq и openssl.
- **Пакет VWARD.** Установлен ровно по `package-map.tsv`, с примерами конфигурации и crontab.
- **Подставные утилиты роутера.** `ndmc`, RCI, `ip`, `ping`, `nslookup`, `wg`, `ps` отвечают
  как исправный Keenetic. `crond` и `tcpdump` скомпилированы, чтобы `ps` видел их как настоящие.
- **Поток DNS.** 70% запросов к популярным именам, остальное к длинному хвосту, 1 запрос/с.

`tests/perf/run-resource-audit.py` запускает службы и под `strace` снимает для каждого задания
cron, демонов и запросов Console:
- **Процессы.** Считаются запуски `execve`; процессы, которые запускают сами подставные
  утилиты, не входят в счёт.
- **Операции с файлами на `/opt`.** Каждое открытие на запись, переименование, создание и
  удаление. Для флешки важно число таких операций: даже 100 байт стоят записи блока и журнала
  файловой системы.
- **Запись в `/tmp`.** Это RAM.
- **CPU и пиковая память.** Отдельные прогоны без `strace`.

Цифры относятся к x86 в CI. На роутере процессор в 10–20 раз медленнее, поэтому важны
отношения «до/после», а не абсолютные миллисекунды. Счётчики на один запуск колеблются
примерно на ±20% в зависимости от состояния: кэши, окна, курсоры.

## Найденные дефекты надёжности

1. **Движок маршрутизации перезапускался каждую минуту.** Это происходило, если нет
   `/opt/var/run/vward`, например на чистой установке без updater. `S91` не мог записать
   pid-файл и каждую минуту считал службу упавшей. Теперь `S91` и надзор за cron создают каталог
   сами.
2. **Поиск процессов зависел от формата `ps`.** Часть сборок BusyBox выводит `{comm}` перед
   командой. `S91` и Console теперь понимают оба формата.
3. **Неудачное обновление списков блокировки повторялось каждую минуту.** При отсутствии сети
   или недоступном источнике планировщик рекламы каждую минуту заново скачивал и перезаписывал
   файлы: около 280 процессов и 137 операций на USB. Теперь повтор не чаще раза в час
   (`SOURCE_RETRY_SEC`, отметка в RAM).

## Что изменено

**Движок маршрутизации:**
- DNS-запросы разбирает один постоянный `awk`. Он пропускает имя, если оно уже обрабатывалось
  в последние 30 секунд; у всех проверок пауза не меньше минуты, поэтому решения не меняются.
- Результаты обычных проверок (`DIRECT_OK`, `NO_IPV4`, `AGH_BLOCKED`, `ISP_FAIL_*`) хранятся в
  RAM, в `/tmp/vward-route-engine-state`. После перезагрузки такие имена просто проверятся
  заново.
- На USB остаются только решения AdaptiveAuto (`AUTO_VPN`, `BROKEN`, `ADAPTIVE_*`). Если есть
  обе копии, читается более новая: policy reconcile по-прежнему публикует `DIRECT_OK` на USB.
- Журнал событий пишет результат проверки, только когда он изменился. Раньше сайт, открытый
  без VPN, записывался каждую минуту.
- Списки групп переписываются, только если изменились. Чтение состояния обходится без `awk` и
  `cat`.

**Контроль туннеля:**
- Снимок здоровья, который пересобирается каждую минуту, перенесён в RAM
  (`/tmp/vward-tunnel-health`).
- Состояние решения остаётся на USB, потому что fail-open нужно отменить и после
  перезагрузки. Но перезаписывается оно только при изменении.

**Защита интернета:** ответы RCI разбираются одним `jq` на ответ вместо одного на поле.

**Реклама:**
- Планировщик считает подпись журнала запросов только в динамическом режиме.
- Своё состояние планировщик пишет на USB только при изменении.
- Временные файлы сканирования, обновления источников и публикации теперь в RAM, если там
  свободно не меньше 32 МБ; иначе, как раньше, на USB.
- Итоговые файлы сканирования (вердикты, правила, очередь проверки) перезаписываются только при
  изменении.

**Updater:** файл настроек разбирается одним `awk`, а не двумя процессами на строку.

**Console:**
- Запрос `status` читает файлы состояния без отдельных процессов и делает один вызов `ps`,
  один `df`, один `jq` для туннелей. Версии утилит кэшируются в RAM до следующего `opkg`.
- Скрытая вкладка браузера больше не опрашивает роутер, а при возвращении сразу обновляется.
- `index.html`, JS и CSS проверяются по ETag (`Cache-Control: no-cache`) и не скачиваются
  заново: 136 КБ JS при каждом открытии стали ответом 304. API по-прежнему отвечает с
  `no-store`.

## Контроль в CI

CI (`resource-audit` в `updater-ci.yml`, под `sudo`) проверяет два пункта:
- `tests/perf/check-route-engine-emulated.py`: настоящий движок в эмуляторе;
  - прямой сайт попадает в RAM;
  - заблокированный провайдером сайт добавляется в AdaptiveAuto на роутере и сохраняется
    на USB;
  - повтор в пределах 30 секунд обрабатывается один раз;
  - после остановки не остаётся процессов.

  На старом коде тест падает.
- `tests/perf/run-resource-audit.py --budget tests/perf/resource-budget.json`: лимиты процессов
  и операций на USB для каждого задания и демона. Отчёт попадает в сводку прогона.

Локально (нужны root, `strace`, `busybox`, `gcc`):

```sh
sudo python3 tests/perf/check-route-engine-emulated.py
sudo python3 tests/perf/run-resource-audit.py --markdown /tmp/audit.md
```

## Не изменено и почему

- **Updater.** Около 20 операций на USB за проверку раз в 15 минут: кэш манифеста, журнал,
  блокировка в `/opt/var/run`. Это путь безопасности с восстановлением после сбоя питания, и
  переносить его ради примерно 2000 операций в сутки на этапе RC не стоит.
- **Блокировки рекламы** в `/opt/var/lib/vward/ads-privacy-guard/*.lock`. Их путь знает
  барьер обновлений; это около 4 операций на скан.
- **Журналы на USB.** Остаются там, чтобы переживать перезагрузку. Объём снизился за счёт
  записи только изменений.
- **Сканирование рекламы на реальном журнале AdGuard Home** в эмуляторе не измерялось:
  подставной AdGuard отдаёт пустой журнал.

## Проверить на роутере

На роутере — только чтение:

```sh
ps w | grep -E '[v]ward-route-engine|[t]cpdump -ni|[a]wk -v window'   # один движок, один tcpdump, один awk
ls /tmp/vward-route-engine-state | wc -l                               # проверки в RAM
cat /proc/meminfo | grep -E 'MemAvailable|Shmem'                       # память и tmpfs
```
