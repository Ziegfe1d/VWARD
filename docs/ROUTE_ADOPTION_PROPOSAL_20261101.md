# Подхват «существующих» маршрутов категорий: предложение (не реализовано)

Статус: **только предложение, код не написан.** Реализация - после явного «ок» владельца.
Основание: read-only проверка 01.11.2026 - адреса части Smart DNS-доменов идут через туннель по
подсетям каталога (например `104.16.0.0/13`), которые есть в Keenetic, но не в
`owned.dynamic.routes`. `reconcile_routes` (`vward-policy-sync.sh`) считает такие маршруты
«existing» (`EXISTING++`) и не записывает их во владение; снимает только `OWNED \ WANTED`
(`TO_REMOVE`). Поэтому вырезание /24 вокруг адреса Smart DNS на них не действует, и утечка
вечная, пока маршрут не чей-то VWARD.

## Что подтверждено кодом
- Сверка удаляет только маршруты из `owned.dynamic.routes`, которых больше нет в нужном наборе
  (после вычитания удерживаемых /24). Маршрут, совпавший с каталогом, но не принадлежащий VWARD,
  не попадает ни в `NEXT_OWNED`, ни в `TO_REMOVE` - не снимается и не разрезается.
- Смена туннеля (`MOVE`) тоже трогает только `OWNED`.
- Тест: `check-policy-smartdns.py` (разрезание только своих), `check-console-diagnostics-dns.py`
  (три исхода диагностики: свой + ждёт сверки, чужой, утечка).

## Вариант подхвата (по шагам, всё только по подтверждению владельца)
1. **Предпросмотр (read-only).** Кандидат: подсеть из активной категории, которая (а) есть в
   `running-config` как `ip route <net> <mask> <туннель> auto` на **нашем** туннеле, (б) не в
   `owned.dynamic.routes`, (в) пересекается с удерживаемым блоком Smart DNS. Маршруты без `auto`
   (ручные), на другом интерфейсе или с нестандартным видом - не кандидаты. Панель показывает:
   список, сколько маршрутов будет снято и сколько добавлено после разрезания, какие домены
   выигрывают.
2. **Backup.** Перед записью: копия `owned.dynamic.routes` и строк `ip route` кандидатов из
   `running-config` в приватный каталог состояния (с меткой времени, права 0600).
3. **Подтверждение.** Явная кнопка с повторением числа маршрутов; без неё ничего не пишется.
   Одна операция - один журнал.
4. **Применение.** Шаг А: только запись кандидатов в `owned.dynamic.routes` (роутер не
   меняется). Шаг Б: обычная сверка разрезает их под действующими защитами (shrink-guard,
   `run_partial`, проверка занятости); массовое снятие - через существующий `--confirm-shrink`.
5. **Откат.** Восстановить `owned.dynamic.routes` из backup и вернуть снятые маршруты строками
   `ip route ... auto` из backup, затем проверить `ip route get` и сохранить конфигурацию. Если
   возврат не подтверждён - сообщение `rollback_incomplete`, backup остаётся.
6. **Не делаем:** автоматический подхват, подхват при обновлении, подхват чужих/ручных/сервисных
   групп, новый демон.

Риск: «existing» может быть маршрутом, добавленным владельцем вручную или прежней версией VWARD;
поэтому только явный выбор и видимый предпросмотр. Тесты (при реализации): 0/1/N кандидатов,
ручной маршрут без `auto`, другой интерфейс, отказ записи, TERM/SIGKILL, откат, параллельная
правка владельцем.
