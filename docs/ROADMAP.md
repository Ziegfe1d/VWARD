## 0. Цель VWARD (владелец, 2026-10-11)

Каждая задача плана проверяется на соответствие этим четырём требованиям.

1. **Лёгкая установка.** Пустая флешка в чистом роутере и одна команда (Termius, Telnet или SSH)
   или файлы на флешке - дальше VWARD всё скачивает и ставит сам.
2. **Понятная Панель VWARD.** Разделы без повторов и лишнего текста; подписи короткие, простые и
   технически правильные («Маршрутизация», «Добавить домен»), без бытовых слов. Панель не
   повторяет Keenetic и AdGuard Home целиком: в ней то, чего нет в прошивке, работа самого
   VWARD и его компонентов, и то немногое из Keenetic/AdGuard Home, что нужно рядом для дела
   (например, включить туннель); за остальным - ссылка в их интерфейс.
3. **Работает сам.** Сам проверяет себя, находит ошибки, исправляет их или находит обходной путь,
   сам обновляется. Роутер никогда не остаётся без интернета.
4. **Обновление без перерыва.** Новая версия ставится рядом с работающей, проверяется и только
   потом становится основной; при сбое остаётся прежняя. Без перезагрузки роутера и без
   обновления страницы вручную.

## 0a. Скелет VWARD: ствол и ветки (решение владельца 12.11.2026)

Основа программы, по которой проверяется каждый новый пункт плана: есть ли он в стволе или в одной
из веток; если нет ни там, ни там, его не делаем (раздел 8).

**Ствол** — у каждого пользователя, не выключается:
1. Маршрутизация делает Keenetic: FQDN-группы и их маршруты (`dns-proxy route object-group`).
   VWARD в путь трафика не встаёт: при сбое VWARD, флешки или Entware Keenetic продолжает
   маршрутизировать списки сам.
2. Go-ядро (`vward-core`): автоподбор доменов и операции списков; дальше — подсети, ответы Панели,
   загрузка и проверка обновлений (вместо curl, jq и lighttpd из Entware).
3. VPN: туннели Keenetic (WireGuard, AmneziaWG с KeeneticOS 5.2, OpenVPN, SSTP …); свой движок
   только для того, чего Keenetic не умеет: VLESS и Trojan через Xray (переключение серверов и
   стран уже есть). Один прокси-движок: Xray; sing-box не берём (раздел 8).
4. Подписанные обновления и Панель VWARD.

**Ветки** — пользователь выбирает сам, по умолчанию выключены:

```
DNS ─┬─ только DNS Keenetic (по умолчанию)
     ├─ + свой DNS для обхода блокировок (Smart DNS)
     │     ├─ до 8 серверов ─────── средствами Keenetic
     │     └─ больше 8 ──────────── dnsmasq + DoH-клиент
     └─ + блокировка рекламы ────── AdGuard Home (Smart DNS тогда внутри него)
VPN ─┬─ туннели Keenetic
     └─ VLESS / Trojan ──────────── Xray
Обход DPI ── по списку доменов (YouTube, Discord …) ── движок nfqws (zapret)
Агенты ── агент VPN · восстановление интернета · IP-категории
Обслуживание ── резервные копии · вход по SSH · флешка · целостность · обновления Entware
```

Правила дерева:
- Одна ветка DNS за раз (Keenetic, dnsmasq или AdGuard Home); Keenetic всегда главный DNS на
  порту 53, ветки стоят за ним. `opkg dns-override` не используется никогда: с ним смерть флешки
  оставляет всю сеть без DNS.
- Ветка ставит и включает только то, что ей нужно; пока её не выбрали, её программ на роутере нет.
- Ветка убирается чисто: выключенная или пропавшая программа не оставляет в Keenetic своих
  DNS-серверов и маршрутов (установщик fix.37 убирает остатки AdGuard Home после форматирования флешки).
- Ветки независимы: реклама без Smart DNS, Smart DNS без рекламы, ни того ни другого.

**Поломка ветки не ломает интернет.** У каждой ветки своя проверка и свой запасной путь; проверка —
часть ветки (пока ветка включена, её проверку отдельно не выключить). Уход — после 2 неудачных
проверок подряд, возврат — после 3 удачных; о каждом переходе — уведомление и запись в журнале.

| Ветка | Сломалось | Куда переходит работа | Сделано |
|---|---|---|---|
| AdGuard Home | не отвечает на DNS | выведен из цепочки; DNS — dnsmasq, если стоит, иначе Keenetic; реклама на паузе | частично (вывод из цепочки в компоненте рекламы, перенести в ветку AdGuard Home) |
| Smart DNS внутри AdGuard Home | AdGuard Home выпал | домены Smart DNS — в dnsmasq (без предела) или Keenetic (до 8); не вместившиеся — через VPN | нет |
| dnsmasq | не отвечает | DNS — Keenetic; домены Smart DNS: 8 в Keenetic, остальные через VPN | нет (ветка не подключена) |
| Сервер Smart DNS (DoH) | не отвечает | его домены (например ChatGPT) временно через VPN, вернулся — обратно | частично (проверка есть, переноса нет) |
| VPN-туннель | лёг | «умный отказ VPN» (ниже); по умолчанию — **ждать** (решение владельца 12.11.2026) | серверы и страны — да; остальное — нет |
| Обход DPI | программа упала или способ обхода перестал работать | трафик идёт мимо неё (в пути трафика без неё ничего не теряется); домены ветки — в VPN; способ подбирается заново | нет (ветка не подключена) |
| Go-ядро | упало | час работает прежний автоподбор; списки в Keenetic не меняются | да |
| Флешка / Entware | умерли | Keenetic маршрутизирует, держит свои туннели и DNS; не работают только Xray и программы флешки | да (при правиле «без dns-override») |
| Панель | упала | ни на что не влияет | да |
| Обновление | не встало | возврат прежней версии | да |

**Умный отказ VPN** (решение владельца 12.11.2026). Домены автоподбора попали в VPN потому, что
напрямую не открылись, — для них «напрямую» бессмысленно; но свои списки владельца не проверялись, а
проверка устаревает. Поэтому при отказе VPN агент сети идёт по шагам:
1. другой сервер, затем другая страна того же туннеля (уже работает);
2. запасной туннель, если он есть;
3. запасных нет — каждый домен VPN-списков проверяется напрямую сейчас: открылся — напрямую до
   возвращения VPN; замедление и включена ветка обхода DPI — через обход DPI; гео-блок сервиса
   (ChatGPT, Gemini, Claude) и включена ветка Smart DNS — через Smart DNS; иначе — ждать;
4. VPN вернулся — всё обратно в VPN, как было.
Для шага 3 автоподбор запоминает, почему домен не открылся напрямую: обрыв соединения, ошибка TLS,
ответ 403/451 со страницей «недоступно в вашей стране», медленный ответ. В «Предполагаемых действиях»
агент сети пишет одно конкретное действие («VPN не отвечает. Ждёт. 12 доменов открываются напрямую —
пустил бы их напрямую»), а не меню; «пустить напрямую» показывается, только если владелец включил его у
агента VPN.

**Обход DPI** (решение владельца 12.11.2026, возвращён из раздела 8): ветка, по умолчанию выключена.
Движок — готовая программа nfqws из zapret (как Xray для VLESS), VWARD ведёт список доменов, подбор
способа обхода (по образцу blockcheck), проверку и запасной путь. Условия: только по списку доменов, не
на весь трафик; при падении программы трафик идёт мимо неё (обязательный режим запуска, без него ветка
не включается); своя проверка — сервис через обход перестал открываться, его домены уходят в VPN, и
обратно; способ подбирается заново, когда перестал работать. Это вмешательство в путь трафика: отдельный
выпуск после fix.38–39, отдельная проверка, на роутер только с разрешения владельца.

**Порядок работ.** fix.38: принципы в реестре частей («что нужно части», «куда переходит её работа»),
выбор ветки DNS в «Компонентах» (Keenetic / dnsmasq / AdGuard Home), «ждать» по умолчанию для VPN без
запасного туннеля. Дальше — «умный отказ VPN» (сначала автоподбор запоминает причину, затем проверка напрямую при отказе) и
переходы по одной ветке за выпуск, каждая с тестом на эмуляторе «сломалась →
интернет работает → вернулась»; первыми — проверка AdGuard Home как часть его ветки и Smart DNS → VPN
при отказе сервера. Это изменения DNS и маршрутизации: каждое — с отдельной проверкой и на роутер только
с разрешения владельца.

**Заморожено** (код остаётся, выключено, не развиваем до решения владельца): реклама и AdGuard Home
(6.5, 6.6), Smart DNS и ИИ-сервисы, режим dnsmasq — будущий механизм Smart DNS вместо AdGuard Home без
предела в 8 серверов (сейчас только строит и проверяет настройки, на роутере ничего не меняет), агент VPN,
восстановление интернета, IP-категории, части агентов (вход по SSH, резервные копии, флешка, целостность,
обновления Entware и AdGuard Home, каталог сервисов), прежний shell-автоподбор и shell-сверка маршрутов
(запасной путь до проверки Go-ядра на роутере), модуль AmneziaWG `vward-awg` (для прошивок старше 5.2).

**Исправить в fix.38 по установке на роутере владельца (12.11.2026):** «Сделать туннелем по умолчанию» и
установщик (перенос с туннеля без настроек) переносят и DNS через туннель - строки `ip name-server СЕРВЕР ДОМЕН on
СТАРЫЙ` (у владельца 16 строк YouTube/Instagram остались на мёртвом `OpkgTun4`); в одной операции со списками и
подсетями, с откатом. Ядро на Go снимает маршрут без `auto` - сделано (51c7527). После «unknown» в журнале ядра
Панель предлагает проверку (`vward-core recover`), а не молча блокирует операции со списками.

**fix.38, «Добавить туннель» по подписке (скриншоты владельца 12.11.2026):** сразу после проверки подписки
роутер проверяет доступность всех серверов (TCP/TLS до host:port с роутера, параллельно, с ограничением времени) и
показывает у каждого «48 мс» или «не отвечает»; сортировка - отвечающие сверху, самый быстрый выбран сам; неотвечающие
свёрнуты в «Не отвечают (N)»; поиск по стране/имени. Строки без адреса (у владельца «Сервер 51 - `:` без шифрования»)
не показывать. Предупреждение «Туннель поднимет Xray… скачивается с GitHub» - только если Xray ещё не установлен.

**fix.38, автоподбор и гео-блокировка (claude.ai, владелец 12.11.2026):** напрямую claude.ai отвечает 302 на страницу
«недоступно в регионе», ядро считает это DIRECT_OK и в VPN не добавляет. Перенаправление на страницу ограничения
(Location с `unavailable`, `region`, `country`, `restricted`, `blocked`, `not-available`) - «напрямую не открылся».
Ответ 403 через VPN от защиты сайта (Cloudflare) - «через VPN отвечает», не «VPN не помог».

**fix.38, «Мои домены» без группы:** если группа для «Моих доменов» не выбрана (после перехода на новый туннель её
нет), VWARD создаёт свою группу через туннель по умолчанию и пишет в неё - вместе с объединением «Моих доменов» с
«Доменными списками». `force-vpn.conf` - только для автоподбора на shell; убрать вместе с ним.

**fix.38.1 (скриншоты владельца с fix.37, 12.11.2026) - сделано, ждёт «Выпускаем»:** каждый доменный список
открывается своей страницей (своя страница «Мои домены» убрана, её содержимое - на странице своего списка); путь любого
списка - ползунок «Авто | VPN | Провайдер», чужой список сначала разрешается менять (list-adopt), затем ставится путь;
туннель сервиса - ползунок (до 4 вариантов); «Восстановление VPN» - режим агента сети на месте; «Агенты» - по
переключателю на агента; две кнопки в ряд больше не выпускают значок за край.

**Удалить из кода (fix.39, перенесено из fix.38):** заготовку sing-box; ремонт пакетов Entware (`opkg --force-reinstall`,

### Правило номеров выпусков (решение владельца 01.11.2026, действует)

- **Целый `fix.N`** (`fix.35`, `fix.36`, …) — очередной полный накопительный выпуск: законченные функции, улучшения,
  исправления и стабилизация. Следующий крупный выпуск получает `N + 1` независимо от прежнего названия пакета в плане.
- **`fix.N.1`, `fix.N.2`, …** (и при необходимости глубже) — быстрые исправления уже выпущенной базы, прежде всего по
  реальным диагностикам и инцидентам; не для заранее запланированных больших функций.
- Опубликованные выпуски, их подписи, `sequence`, коммиты, CI и история `CHANGELOG.md` задним числом не переименовываются.
- `sequence` подписанной ленты — технический монотонный счётчик, отдельный от `VERSION` для человека. Поля «версия для
  человека / машинный идентификатор / дата / номер сборки» — отдельная будущая задача, в fix.35 не реализуется.
- Порядок по компаратору updater (тест `check-version-numbering.py`): fix.34.1 < fix.35 < fix.35.1 < fix.35.2 < fix.36.

- **Одна компактная строка под названием VWARD:** `Версия 0.2.0 RC2 #35.0.261101`. В основной строке не показывать слова «fix», «выпуск», «исправление» и служебную SemVer-запись.
- **Формат `#N.P.ГГММДД`:** `N` — сквозной номер полноценного накопительного выпуска; `P=0` — основной выпуск; `P=1,2,...` — быстрые исправления (в том числе критические) к этому выпуску; `ГГММДД` — фактическая дата сборки. Дату получать автоматически из данных выпуска, а не придумывать вручную.
- **Примеры на RC2:** `0.2.0 RC2 #35.0.261101` (основной), `0.2.0 RC2 #35.1.261102` (быстрое исправление), `0.2.0 RC2 #36.0.261110` (следующий основной).
- **После выхода из RC/RP:** убрать обозначение предварительного этапа: например, `Версия 0.2.0 #45.0.270115`; следующие версии продукта могут быть `0.2.1`, `0.3.0`, `1.0.0` по смыслу изменений. Эти будущие номера и даты — только примеры, не утверждённый график.
- Номер `N` не сбрасывать при переходе RC → RP → RETAIL; опубликованный идентификатор `N.P` не использовать повторно для другого содержимого. Дата не определяет порядок версий и не заменяет отдельный технический счётчик обновлений.

действующего покрытия, не вводя лишних ожиданий. Если домен уже маршрутизируется
нужным образом, не создавать повторное правило лишь ради записи в AdaptiveAuto.
При выключении другого источника пересчитывать покрытие, не теряя сохранённые
настройки и историю. Явные пользовательские исключения/маршруты уважать.

**Общий принцип для любых сервисов и доменов (YouTube — лишь пример):**
не допускать разрастания конфигурации одинаковыми физическими группами,
FQDN/DNS-привязками и маршрутами при повторном включении «Сервисов»,
автоподборе, обновлении каталога, перезагрузке или переустановке.
Перед созданием проверять уже существующее покрытие во всех включённых
источниках, в том числе группы пользователя; подхват возможен только с
проверкой принадлежности, названия, состава доменов, назначения VPN/ISP
и прав на изменение. Совпадающий домен не повод создать новую группу,
а частичное совпадение не повод слить независимые пользовательские правила.
В Панели один логический сервис может ссылаться на несколько источников,
но без избыточных технических копий; показывать происхождение и итоговый
маршрут. Устранение ранее созданных дублей — только по отчёту, с копией
и явным согласием на изменение пользовательских групп. Критерий приёмки:
повторная операция не увеличивает число эквивалентных групп и маршрутов,
при этом автоподбор по-прежнему дополняет новыми доменами.

**Детальная логика выбора активных источников (проектная модель, подтвердить аудитом):**
- Сначала раздельно определить **наличие** источника, **разрешение владельца на его
  использование**, **владение группами** и **фактически действующие маршруты**. Пустой
  или отсутствующий ручной список — штатное состояние, не причина выключать
  «Сервисы» или «Автоподбор доменов». Включённый, но пустой источник работает
  как источник без доменов. Кнопка «Использовать» не должна подразумевать
  автоматическую активацию всех записей каталога «Сервисы»: учитываются только
  отдельно включённые сервисы.
- При всех выключенных источниках VWARD не создаёт и не обновляет доменные
  маршруты. Сторонние правила Keenetic при этом могут оставаться действующими,
  поэтому Панель обязана их обнаруживать и не утверждать, что интернет весь
  идёт напрямую. Базовая цепочка DNS/AdGuard Home и интернет не отключаются.
- Таблица M = ручные, S = Сервисы, A = Автоподбор; 1 — разрешён, 0 — выключен:

  | M | S | A | Ожидаемое поведение VWARD |
  |---|---|---|---|
  | 0 | 0 | 0 | Не применять VWARD-доменные маршруты; чужие правила отдельно |
  | 0 | 0 | 1 | Только Автоподбор, если найдена подтверждённая потребность |
  | 0 | 1 | 0 | Только конкретные включённые Сервисы |
  | 0 | 1 | 1 | Сервисы + новые непокрытые домены Автоподбора |
  | 1 | 0 | 0 | Только разрешённые ручные списки |
  | 1 | 0 | 1 | Ручные списки + новые непокрытые домены Автоподбора |
  | 1 | 1 | 0 | Ручные списки + включённые Сервисы |
  | 1 | 1 | 1 | Все три источника, без лишних повторных маршрутов |

- При подборе домена: (1) нормализовать и сопоставить точные имена и покрытие
  поддоменов в соответствии с **фактической** семантикой FQDN Keenetic;
  (2) проверить все реально действующие маршруты и Smart DNS/DNS-исключения;
  (3) собрать желаемые назначения только из разрешённых источников;
  (4) при одинаковом результате повторно использовать существующее покрытие
  без новой физической группы; (5) при противоречии VPN/ISP или выборе разных
  туннелей — показать конфликт и источник, не менять чужой маршрут молча;
  (6) для нового подтверждённого домена допустить запись Автоподбором с
  проверкой результата. Не считать, что одинаковый IP из общей CDN означает
  один и тот же домен или допустимость переноса всей подсети.
- Приоритет на оценку: явно заданные пользователем правила и исключения —
  выше каталожной рекомендации, Автоподбор ниже обоих; но реальный конфликт
  существующих маршрутов не «разрешать» только этой таблицей, пока не проверен
  фактический маршрут клиента. Запрет на прямой выход при падении VPN или
  допустимость запасного ISP — отдельная явно показанная политика безопасности,
  без молчаливой смены пути. Если действующего туннеля нет, не ставить маршрут
  в пустоту и не создавать повторные записи; сохранить намерение и причину.
- При отключении источника уменьшать только принадлежащее VWARD покрытие,
  которое более не требуется другим источникам; общие записи удалять только
  после проверки ссылок и владения. При включении — пересчитать желаемое
  состояние, а не восстановить устаревшие DNS/Smart DNS-снимки вслепую.
  Все изменения — под одной согласованной блокировкой, атомарно и с откатом;
  обработка повторной команды должна быть идемпотентной.
- **Обнаруженная опасность по исходникам 30.10 (не проверена на роутере):**
  `vward-console-config.sh` функция `service_adopt()` выбирает существующую
  группу по названию либо >=80 % совпадения доменов, а `service off` затем
  выполняет `no object-group fqdn $G` без отдельной проверки, создана ли
  эта группа пользователем. `services-refresh` также меняет содержимое
  групп из `enabled.tsv`. При подхвате чужой группы это потенциальная потеря
  пользовательских данных/маршрута. До безопасной интеграции требуются
  доказательство воспроизводимым тестом, строгая метка владения и режим
  **reference-only** для ручной группы: сервис может видеть её покрытие, но
  не вправе менять её состав, маршрут, удалять её при выключении или переписывать
  при обновлении каталога. Пока различие не подтверждено, не подхватывать группу
  для мутации. При необходимости привести ручной маршрут к другому туннелю —
  отдельное предложение владельцу, не автоматическая запись.
- Нужен план миграции для старых `enabled.tsv` без признаков владения:
  неизвестное происхождение считать чужим до подтверждения; безопасная
  read-only классификация, затем согласованное переназначение ссылок. Сверка
  после перезагрузки/обновления не должна превращать ссылку на чужую группу в
  право владения. Физические группы создаются только для отсутствующего
  полезного покрытия с учётом лимитов Keenetic (включая 300 FQDN на группу).
- Панель: для каждого источника показывать включение, доступность, фактическое
  применение, число уникальных доменов, перекрытия, конфликты, чей список,
  и причину «настройка не может выключить чужой маршрут». Для сервиса —
  **одна логическая карточка**, даже если покрытие поступает из ручной группы,
  каталога и Автоподбора; отдельно показывать физические группы и отклонения.
  Не создавать новый страж/периодический обход ради этого: оценить использование
  имеющихся снимков `running-config`, кэша и цепочки сверки.
- Дополнительные тесты: отсутствие ручных групп; пустые/выключенные источники;
  все 8 сочетаний; идентичные и частично совпадающие каталоги; конфликт ISP/VPN;
  независимые ручные правила при выключенном VWARD; повторное включение сервиса
  после удаления `enabled.tsv`; adoption -> off, adoption -> catalog refresh
  для чужой группы (она должна остаться неизменной); переключение источника
  при активном Автоподборе; падение VPN, DNS/AGH/RCI, переполнение FQDN;
  несколько параллельных изменений, перезагрузка/обновление и откат.
  Метрики: число физических групп не растёт от повторных операций, чужие
  правила не меняются, время/нагрузка не хуже исходного режима.

### 5.8 Где живёт туннель: целиком в Keenetic или целиком в VWARD
