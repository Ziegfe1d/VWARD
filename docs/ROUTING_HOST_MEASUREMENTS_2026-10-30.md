## Что исполнялось

`tests/perf/measure-routing-host.py` извлекает функции из актуальных исходников
без переписывания их алгоритмов. Единственная замена внутри функции:
`membership_state` пишет временный снимок в приватный TemporaryDirectory вместо
глобального `/tmp/vpn-reconcile-verify.$$`. Транспорт — локальный fake `ndmc`,
который принимает только `show running-config`; любая команда записи завершает
прогон ошибкой. Admission не вызывается этим изолированным набором функций;
PID oracle, проверки продукта и штатные CI-тесты не подменяются.

Каждый образец получает новый одинаковый fixture: N уникальных доменов в
`domain-list0`, N в `AdaptiveAuto`, N маршрутов `/24` и тот же owned CIDR.
Размер конфигурации: 969 байт при N=8; 31 189 байт при N=300. Каталоги и
начальное локальное состояние создаются до измерения. DNS и сеть не используются.

| Сценарий | Реальные функции | Работа одного образца |
|---|---|---|
| policy-sync-noop | prefix_mask, route_line, reconcile_routes | Один снимок, сверка N уже установленных собственных маршрутов; нет add/remove/save |
| policy-membership | group_members, membership_state | N последовательных подтверждений присутствующего домена; каждое требует свежий снимок |
| adaptive-fresh | adaptive_names | 1 + min(8,N) чтений списка, существующий VWARD_RECONCILER_ONE_LOOK=0 |
| adaptive-cached | adaptive_names, _vward_kc_fresh, vward_keenetic_config | Столько же чтений, ONE_LOOK=1; холодный приватный cache, AGE=60 с |

AdaptiveAuto здесь выполняет девять чтений без изменений конфигурации, а не
полный reconciler с пробами/удалением. Лимит восьми обрабатываемых доменов продукта
сохранён. AGE=60 нужен только для непрерывности синтетического образца;
это существующий параметр fixture, конфиг продукта не меняется.

## Метод и границы счётчиков

Три повтора, чередование порядка сценариев и размеров, без прогрева. У каждого
повтора отдельный прогон учёта и отдельный прогон стоимости: всего 48 процессов
верхнего уровня; таймаут каждого 30 с. CLI разрешает максимум четыре размера
1…2000, пять повторов и таймаут 60 с; бесконечного stress-цикла нет.

- Снимки и внешние операции считаются по журналу fake transport; проверяется
  точный список команд. Во всех образцах RCI/DNS/probes/mutations/save = 0 по
  конструкции этих сценариев, а не по наблюдению полного приложения.
- Внешние инструменты: отдельные wrappers всех BusyBox applets записывают каждый
  запуск через PATH. Счётчик включает `cat` fake transport; проверка результата
  выполняется Python после измерения. Это число обращений к инструментам,
  **не** число execve: реальный ash умеет исполнять часть applets без exec.
- CPU user+system — `wait4` отдельного неинструментированного процесса и его
  ожидавшихся потомков, включая маленький native launcher `busybox time`.
  RSS берётся из `busybox time -f %M` для workload и его потомков: максимум
  одного процесса, не сумма одновременных RSS. Это устраняет высокий RSS,
  унаследованный прямым Python child до exec. Wall включает запуск и опрос
  завершения Python с шагом 5 мс; быстрые образцы имеют соответствующую погрешность.
- Байты workspace — сумма логических размеров оставшихся обычных файлов внутри
  payload до/после неинструментированного образца. Это **не** cumulative writes,
  peak temporary usage, занятые блоки, запись на USB/флешку или wear. Например,
  временный membership-снимок удаляется до конца, поэтому его нет в final bytes.
  Дополнительно JSON содержит точное число байт ответов fake transport.

`strace` установлен, но smoke получил `PTRACE_TRACEME: Operation not permitted`.
Поэтому здесь использован `--accounting wrappers`, а точные execve, создания
процессов и cumulative write bytes явно равны `null`. Для среды с ptrace есть
режим `--accounting strace`: парсер учитывает только успешные syscalls и записи
в payload. Он проверен unit-тестом; реальный traced workload здесь не исполнен.
Сырые traces не сохраняются. Ни наличие strace, ни wrappers не выдают эти
неизмеренные значения за измеренные.

При N=300 policy-sync выполняет 600 grep, membership — по 300 awk/cat/grep/rm/tr.
Существующий cache снижает число внешних снимков AdaptiveAuto с 9 до 1
(ответы 280 701 → 31 189 байт), но требует 58 вместо 36 локальных обращений к
инструментам. На fake с практически нулевой задержкой он не выигрывает CPU;
это не основание отключать cache на реальном медленном Keenetic.

Сравнивать можно один сценарий при 8/300 или paired fresh/cached при одинаковом N.
Между разными сценариями разное число проверок; таблица не ранжирует компоненты
по общей эффективности. Хост общий, нет CPU isolation; три повтора не дают
надёжных percentile/regression thresholds. Ресурсные бюджеты не менялись.

## Решение и воспроизведение

Оптимизация продуктового кода отложена обоснованно. Линейные grep policy-sync
подтверждены, но замена сверки требует отдельного RED→GREEN покрытия `/32`,
shrink/Smart DNS, смены цели и отказов ndmc. Свежие снимки membership после
мутации защищают от неизвестного/устаревшего состояния; сокращать их только
по этой таблице нельзя. Исправления console-config идут отдельным пакетом.

```sh
VWARD_MEASURE_BB=/path/to/busybox
python3 tests/repository/check-routing-measurements.py
python3 tests/perf/measure-routing-host.py --busybox "$VWARD_MEASURE_BB" \
  --accounting wrappers --sizes 8 300 --repeats 3 --timeout 30 \
  --output /tmp/routing-host.json
```

Фактически использован BusyBox
`/workspace/scratch/e84db2529462/rs-validation/tools/unpacked/usr/bin/busybox`;
SHA-256 закреплён в JSON. Smoke N=2 прошёл все четыре сценария. Unit accounting
прошёл RED→GREEN: отсутствующий harness, затем отдельный отсутствующий RSS parser;
итог 5/5. Полные тяжёлые suites, CI и аппаратная приёмка здесь не запускались.

Разрешённые выводы: воспроизводимые количества снимков/обращений и рост работы
этих функций на одинаковых синтетических данных. Нельзя заявлять снижение
load average/CPU/RAM/flash на Viva, RCI latency, улучшение клиентского пути,
поведение DNS/IPv6/UDP, лимит маршрутов или достижение критериев P-7.
Для этого остаются штатный CI/эмулятор и согласованная аппаратная приёмка.
