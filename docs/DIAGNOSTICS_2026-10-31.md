# Диагностика Keenetic KN-1913 (5.01.C.8.0-2) от 31.10.2026 — разбор

Источники: `vward-all-2026-10-31.txt` (журналы VWARD) и self-test Keenetic (19:44 МСК), присланные
владельцем. Секреты, токены и приватные DNS-URL в репозиторий не переносятся (в разборе только
структура правил). Роутер не менялся. Wi-Fi по решению владельца исключён.

## P0. Автоподбор доменов: цикл START_FAILED / TERM — причина найдена, исправлено

**Факты журнала (19:13–19:51):** 41 `START_FAILED|wait=12s|last_stop=none`, 42 `STOP|reason=TERM|rc=143|ran=13–14s`,
старт каждую минуту в `:02` (тик cron/watchdog). Почти в каждом старте
`PERSIST_RESTORE_OK|added=0|removed=0|skipped=0|over_limit=0|left=0` через **8–13 с** после `START`;
19:17:02 — вовсе без OK за 13 с. В self-test (19:44:51) у S91 запущены 3 процесса
`vward-route-engine.sh` и `curl … 127.0.0.1:79/rci/show/running-config` (max-time 30); load average 5,79,
память MemAvailable 81 MB из 254 MB (память не причина).

**Причина.** `restore_adaptive_from_persist` при `added=0 removed=0` не делает ни одного вызова
ndmc — значит 8–13 с ушли на чтение `show running-config` (RCI/ndmc). После restore движок ставил
`REFRESH_TS=0`, поэтому `refresh_sets` читал конфигурацию **второй раз напрямую** (в обход общего
кэша). Захват (dnscap/tcpdump) стартует лишь после всего этого, а S91 ждёт его 12 с → `START_FAILED`,
`clean_service` посылает TERM, на следующей минуте всё повторяется. Старт совпадает с тиком cron,
когда другие агенты тоже читают конфигурацию, и direct-чтение не использовало их кэш.
Конкурирующих экземпляров и остаточных процессов не видно: блокировка и `last_stop=none` согласуются
с убийством S91, а не с падением движка.

**Исправление** (`fix-engine-start-reads-20261031`): restore и refresh используют общий кэш
(`shared_config`, возраст ≤ `VWARD_KEENETIC_AGE`), принудительный refresh — только если restore
реально изменил группу (запись ndmc сбрасывает кэш). Таймауты и задержки **не менялись**.
RED→GREEN: `tests/repository/check-route-engine-start-reads.py` (2 чтения → 1; после реальной
записи — 2, корректность сохранена). **Не доказано без устройства:** укладывается ли теперь старт
в 12 с при самом медленном RCI. Критерий приёмки (read-only, одна команда для Termius по
`docs/termius-standard.md`): после обновления в `vward-route-engine-events.log` за час нет
`START_FAILED`, а `grep -c START_FAILED` не растёт. Если одно прямое чтение само занимает >12 с,
потребуются данные `vward-keenetic-slow.log` и отдельное решение (запуск захвата до restore).

## P1. IP-категории: `targets=484 ok=4 fail=281 unknown=86 nodns=113` — дефекта логики нет, есть ложная трактовка

- `fail` = класс `ISP_BAD`: ISP-проба не прошла (timeout/ошибка), **а через туннель сайт ответил**
  (2xx/3xx/4xx кроме 451). Это не «403/404 = блокировка» и не «таймаут = блокировка»: решает пара
  проб. Ответ 5xx от ISP → `UNKNOWN` (не блокировка), 451 → `UNKNOWN`.
- `unknown` = обе пробы не дали вывода; `nodns` = у цели нет IPv4 (113 стабильно).
- Аудит **ничего не маршрутизирует**: он пишет только `candidates` (прямой маршрут после ≥3 подряд
  `DIRECT_OK`). Сейчас 1–2 кандидата. Маршруты по недоказанным результатам не добавляются.
- Тренд `ok` 53 → 4 за 10 ночей при стабильных `fail≈281` — похоже на деградацию прямого пути
  ISP/сайтов, но по одной ночной пробе без повторов это гипотеза, не доказательство.
- Ложное в **подписи** итоговой строки: `vpn_down` (77) значит «ISP и VPN-проба по этому сайту обе
  не удались», а не «туннель упал» (падение туннеля — отдельные `ABORTED_TUNNEL_DOWN`/`SKIPPED`,
  за 31.10 не было); `isp_timeout` (282) смешивает `ISP_BAD` (VPN ответил) и `UNKNOWN`.
  Исправление — только диагностическая переименовка причин; отложено в ROADMAP (тест
  `check-policy-audit-pause.py` фиксирует нынешние имена, менять вместе с ним).
- Ночное окно: ~2000 с на ~500 сайтов, `paused` 210–600 с (пауза по `vward_busy`), 00:36–00:53 —
  согласуется с нагрузкой RCI.

## P1. RCI: `rci_unavailable` — нестабильность не подтверждена как текущая

Из 100 событий `rci_unavailable` 82 приходятся на 24.10 и 11 на 25.10; за 31.10 — 2 (оба с
`probes=ok class_kept=HEALTHY`). Действий восстановления нет: `recovery_count=0 recovery_stage=0`,
ни одного `RECOVER`/`recovery_stage>0` в журнале «Интернет». Код уже не перезапускает подключение
из-за временной недоступности RCI. Дефекта нет. Сопутствующий фактор — P0: лишние прямые чтения
конфигурации нагружали RCI (теперь убраны на старте движка).
