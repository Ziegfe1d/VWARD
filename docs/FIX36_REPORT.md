## Движок

Подтверждённый источник второго корня: две ветки `handle_host` (ручной домен,
AdaptiveAuto) запускали `( { agh_bind; nslookup; } & )`. Внутренняя оболочка
становится сиротой с PPID=1 и argv движка. `adaptive_live_pids` выбирает точное
поле скрипта, поэтому awk list-watch не считается; `adaptive_core_count` исключает
только потомков найденных оболочек. Счётчик правильно отличает второй корень,
но старый движок сам создавал его. `by=` — вызывающий S91, не личность второго ядра.

Регрессия на настоящих процессах: работа 0,5 с даёт `2 -> 1` после перепроверки,
3,5 с — `2 -> 2`, с оставленным после выхода родителя процессом. Именно временем
жизни/моментом проверки объясняется разная реакция в предоставленных событиях;
личность конкретных PID 10:19/10:26/10:28 задним числом не восстановлена.
Теперь задачи остаются детьми Live, их PID учитываются и ожидаются при выходе.
Вложенная command substitution проверена отдельно: убийство только рабочего
родителя также создавало сироту; штатное завершение ждёт работу, S91 сохраняет
свой ограниченный stop всего дерева. Подсчёт, повторная проверка и защита от
независимого второго движка не изменены.

Источники запуска: cron-watchdog раз в минуту; supervisor recover_critical и
start_of по запросам realtime/network; boot, Панель/смена туннеля, vward-off,
возобновление updater. S91 start/stop/restart сериализуются CONTROL_LOCK;
service_healthy требует PIDFILE=LIVE_LOCK/pid, живой PID и ровно один корень.
clean_service останавливает все найденные оболочки/захват и снимает runtime-файлы.
Второй вызов S91 сам по себе новый Live при здоровом первом не запускает.

Воспроизведена задержка общей копии конфигурации: убитый читатель оставлял
pid-less lock; следующий ждал до 35 с, затем читал конфигурацию. Новые leases
содержат реальный PID оболочки (builtin `/proc/self`, не наследуемый `$$`),
точечное удаление только мёртвого владельца, отдельный временный файл читателя.
Живой читатель не лишается lease по возрасту. Конкурирующие читатели сохраняют
одно чтение. Старый pid-less lock обслуживается прежним правилом возраста.
Связь именно этого механизма с каждым стартом 34–39 с на Viva — гипотеза:
в исходном журнале нет снимков cache lock и этапов. Добавлены START_PHASE
restore/agh-prune/refresh с реальными elapsed/total/rc. Таймауты не увеличены.
Read-only вывод владельца в 10:50: один корень; running-config обычно 4,2–5,2 с,
отдельные 6,75/7,8/9,32 с. Нагрузка ndm этими строками не измерена.

## WAIT_DEGRADED

Health: исправный локальный интерфейс + хотя бы одна из двух HTTP-проб
через туннель (`1.1.1.1`, `1.0.0.1`); явный config/link down отменяет UP.
Первая плохая проверка — DEGRADED, вторая подряд — DOWN. Guard на DEGRADED
обнуляет down_streak и ждёт, не выключает туннель. `active=0` означает, что
fail-open guard сейчас не активен; это не число подключений и не отсутствие VPN.
Handshake не определяет GOOD; у Xray возраста WireGuard handshake может не быть.
Read-only в 10:50: UP, FAIL_COUNT=0, OK_COUNT=32, config/link up, обе пробы=1.
Состояние туннеля сейчас исправно. Причина единичной проверки 10:18 не доказана:
возможны реальный краткий отказ/задержка пробы, но ежедневная строка сама по себе
не доказывает длительный разрыв. Две пробы используют Cloudflare, поэтому не
покрывают независимые сети. Логику health в этом пакете не меняли.

## Безопасные действия Панели

Режим DNS использует только явно настроенный Smart DNS, свежая неудачная или
неизвестная проба запрещает запись. Keenetic сохраняет лимит 8, включая чужие
строки. Пересечения с другими группами запрещены; их membership включён в
before/after каждого шага, изменение во время операции закрывает компенсацию.
Приватный журнал и точные scope-образы пишутся до команды; потерянный ответ
различает исполненную/неисполненную команду по свежему чтению. Неизвестное
состояние/SIGKILL оставляет `BACKUP_DIR-recovery/smartdns.*` и запрещает следующую
запись штатным routing recovery gate. Автоматического replay нет.

Постоянный proof содержит точный список собственных DNS-строк и identity группы.
Чужие существующие DNS не становятся собственными. Пока DNS активен, старые
редакторы доменов/clear/delete/merge/adopt-off запрещены с объяснением; сначала
нужно явно выбрать другой путь. Watch=1 проходит через DNS→auto transaction.
Внешнее изменение списка/DNS отзывает proof и требует разбора, без слепой записи.
Операция идёт через существующий detached job, поэтому 20-секундный HTTP timeout
не оставляет интерфейс с ложным завершением. Массовый выбор сохраняет существующий
контракт отдельных транзакций, результат каждого списка показывается отдельно.
Лимит суммарных добавлений учитывается также в доступности общего переключателя.

Установка dnsmasq-full/sing-box-go: только отсутствующий allow-listed пакет,
ровно один настроенный официальный feed bin.entware.net, HTTP заменяется HTTPS,
TLS downgrade запрещён. Размер/SHA256/архитектура/установленные зависимости,
имена и типы tar-членов проверены до extraction; symlink/hardlink/traversal
запрещены. Панель не выполняет непроверенные maintainer scripts. Проверка чужих
файлов и symlink-родителей выполняется под package lock. Новые пакеты остаются
выключенными, auto-права не меняются. Если зависимости отсутствуют, установка
явно отказывается и не тянет их неявно. При неизвестном откате штатный pending/
unknown gate сохраняется. Удаление/сброс/переустановка из Панели не добавлялись.

Официальный HTTPS индекс Entware прочитан с хоста разработки (не с роутера):
в mipselsf-k3.4 опубликованы dnsmasq-full 2.92-1 и sing-box-go 1.13.3-2 с
Architecture=mipsel-3.4 и SHA256. Это не доказательство архитектуры устройства
или работы программ на Viva. Архитектура выбирается по его opkg.conf, не по имени
модели. Бинарники на роутере не запускались и пакеты туда не устанавливались.

Xray: существующая официальная загрузка и закреплённая SHA-256, без запуска
туннелей. Внутренний install lock сериализует также вызовы вне Панели. Проверки
версии повторены под lock и перед commit; временный pending уникален, его снимает
только владелец. При незавершённом commit сохраняется приватный before-image и
install.pending; при SIGKILL stale install lock требует разбора, не автоматического
удаления. Параллельная установка, отказ version-target и смена его на каталог
во время загрузки получили регрессии. Панель не устанавливает отсутствующий
движок поверх уже настроенных туннелей, чтобы установка не активировала их.

## Откат

Код — штатный файловый rollback Update Engine к fix.35.1, без ослабления Ed25519,
SHA256, admission, health profile full и каталога подписанных пакетов. Файловая rehearsal с подписанным baseline fix.35.1 прошла 13/13: полный health,
сохранность чужих файлов и побайтовое восстановление каждого baseline файла.
Исходный штатный script использован с другим baseline в приватном workspace;
rehearsal key не опубликован, feed не изменялся.
Операции Панели не входят в файловый rollback: DNS возвращает только собственные
подтверждённые дельты, пакетная установка — образ/удаление только своей операции.
При UNKNOWN сохраняются приватные данные; общий rollback кода не выдаётся за
автоматическое восстановление конфигурации Keenetic/Entware.
