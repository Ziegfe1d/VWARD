только настройкой по умолчанию в выпуске, с возможностью включить обратно.

## 2. Скорость Панели (шаг 2)

Источник: `tests/perf/measure-panel.py` (новый, диагностика): каждый запрос страниц
(`LOADERS`/`PAGES` в `vward-console.js`) холодный (кэши пусты) и тёплый, и тумблеры (POST), под strace
на эмуляторе. Оценка Keenetic = процессы × 10 мс + `show running-config` × 4 с + прочие ndmc × 0,3 с
+ RCI × 0,1 с. Эмулятор — маленькая конфигурация; на роутере владельца она больше (1 257 `ip route`).

| Страница | запросов сразу | холодная: самый долгий / сумма работы, с | тёплая (обновление каждые 15 с) |
|---|---:|---|---|
| Обзор | 10 | **4,8** / 18,9 (`status`) | 0,8 / 2,7 |
| Сеть, VPN, Маршруты, DNS, Настройки, Компоненты | 5–9 | **4,8** / 9,5–14,1 | 0,8 / 1,5–2,1 |
| Система | 12 | **4,8** / 15,3 | 0,8 / 3,2 |
| Реклама | 6 | 0,4 / 1,0 | 0,4 / 1,1 |

**Что медленнее 2 с и почему:**

| Действие | Сейчас (оценка Keenetic) | Почему | Что сделать |
|---|---|---|---|
| Смена сервиса / ИИ-сервиса / туннеля (ядро B) | ≈ 56 с; первый запрос ≈ 150 с | 3 600 процессов (10 400 у первого) и 5 (12) полных чтений конфигурации | Go-ядро: 2 узких чтения + 1 пачка RCI (§3); Панель — фоновая задача «применяется…» |
| Домен в список: добавить / убрать | ≈ 9 с / 4,5 с | 2 и 1 полных чтения `show running-config` на одну строку | одна команда + проверка узким чтением группы |
| Первое открытие почти любой страницы | ≈ 4,8 с | `status`, `config-data`, `ai-data`, `awg-data`, `wifi-data`, `lists-data`, `list-data`, `diagnostics` читают всю конфигурацию, когда копия старше 55 с | файл состояния, обновляемый фоном (одно чтение на всех, узкими запросами), страница читает файл |
| Тумблер во время долгой операции | 10 с ожидания, затем «занято»; браузер сдаётся на 20 с | общий замок правок (`edit_lock`, 10 × 1 с), долгие операции держат его десятки секунд | замок только своей области; долгие операции — отдельной очередью |
| Холодная страница целиком | 6–12 CGI одновременно = 100–400 процессов (1–4 с CPU на 2 ядрах) | каждый запрос заново подключает библиотеку профиля (1 400 строк) и jq | один запрос «состояние страницы» из файла состояния |
| `diagnostics` | 3,4 с даже на x86 | сетевые пробы в запросе | фоновой задачей с «выполняется…» (как сейчас кнопка), страница — последний результат |

Укладываются в 2 с уже сейчас (если не ждут замок): режим агентов, тумблеры сторожей, классификатор,
Wi-Fi, пауза рекламы — 30–58 процессов, 0,3–0,6 с; около 30 из них — вход `vward-console-config.sh`
(проверки восстановления маршрутизации) и для немаршрутных тумблеров не нужны.

**Узкие запросы RCI.** В коде уже используются: `show/interface`, `show/internet/status`,
`show/ip/hotspot`, `show/associations`, `show/object-group/fqdn`, `show/version`, POST `/rci/`
`[{"parse":…}]` (секреты туннелей). Для маршрутизации прототип читает `object-group/fqdn` и
`dns-proxy` (поддеревья конфигурации) вместо всей конфигурации; на KeeneticOS 5.1.8 это
проверяет `vward-core dry-run` на роутере: строки `NARROW_EQUALS_FULL` сравнивают узкое и полное
чтение по группам, маршрутам и строкам Smart DNS. Пока равенство не доказано на роутере, ядро
читает конфигурацию целиком через RCI (без процесса ndmc).

## 3. Прототип Go-ядра маршрутизации (шаг 3)

`tools/vward-core` — Go, только стандартная библиотека, статическая воспроизводимая сборка как
`tools/vward-awg` (`build.sh OUT --check`, `GOTOOLCHAIN=go1.25.1`, `-trimpath -s -w`). В этой сборке
**нет пути записи**: команды `version`, `probe`, `dry-run` только читают; исполнитель работает
только в тестах.

- `internal/rci` — свой HTTP/1.1-клиент к 127.0.0.1:79 (без net/http), жёсткий режим «только чтение»
  (GET и `show …`), одна пачка команд = один POST.
- `internal/decision` — `vward_routing_choice`, `vward_routing_service_policy`, `vward_routing_audit`
  перенесены побайтно; тест равенства с shell-оригиналами на sh и BusyBox (2 000 сгенерированных
  случаев, ≥ 25 % принятых, мутации ловятся). Модель владельца `Resolve`: ручные > сервисы >
  Автоподбор, Авто/VPN/Провайдер/DNS, один домен — одно назначение, лимит 8 строк DoH (чужие
  строки считаются), мёртвый сервер → запасное правило с причиной, `.ru`/`.рф`/`.su` не в
  Автоподбор, UNKNOWN не решается, VPN при 0/1/2/3 туннелях без прошитых имён.
- `internal/ndm` — модель конфигурации из полного текста и из узких JSON; подпись владения
  побайтно равна `service_signature` shell (тест на sh и BusyBox).
- `internal/plan` — разница «желаемое ↔ текущее» только для своих групп; чужие и неизвестные —
  отказ «foreign», домен, который чужая группа уже ведёт в другой туннель, — отказ
  «foreign-coverage»; `ip route`, `ip name-server`, NextDNS и системные команды запрещены защитой.
- `internal/journal` — та же семантика, что `vward-routing-journal.sh`: каталог на операцию,
  атомарные записи с fsync, pending до отправки (пред- и ожидаемое пост-изображение областей),
  resolved > unknown > done|failed > pending, pending/unknown блокируют новые, id не повторяется.
- `internal/exec` — gate → CAS узким чтением затронутых областей непосредственно перед пачкой →
  pending → **одна пачка RCI** → одно узкое чтение → доказательство каждого шага; иначе
  компенсация до пред-изображения (строки Smart DNS — только свои) и `failed`, или `unknown`.
  Повтор без изменений — без чтений, журнала и записи.
- Тесты исполнителя на поддельном Keenetic (своя реализация состояния): узкое = полному; сервис —
  одна пачка, 2 чтения, ни одного полного; смена туннеля при 2 и 3 туннелях; чужое не трогается;
  8 подсетей Google, 16 правил на OpkgTun4 и NextDNS неизменны после каждой операции; сбой
  посередине → откат до исходного; потерянный ответ после/до применения → done/failed; правка
  между планом и отправкой → отказ без отправки; pending блокирует; лимит 8 DoH.

**Замер на эмуляторе (x86):** конфигурация масштаба роутера владельца (40 групп, сервис из 175
доменов, 1 257 `ip route`, 16 `ip name-server`): полное чтение 2 мс, узкое 3 мс, план 0 мс,
симуляция тумблера на 175 доменов 1 мс CPU, RSS 6,3–9,2 МБ (64-бит). Бинарник mipsle 3,3 МБ
(1,1 МБ gzip). Время на Viva зависит от ответа ndm на RCI — его и меряет команда ниже.

**Что не перенесено (честно):** снимок/импорт legacy-форматов (`vward-routing-legacy.sh`,
`-snapshot.sh`), миграция, источники M/S/A из сохранённого состояния, Smart DNS сервера,
восстановление после сбоя питания (`Open`/`Resolve` есть, процедура — нет), подключение к API/Панели.
Существующие shell-тесты PR #38 (~77 проверок) пока гоняют shell-ядро; для Go перенесены
сценарии владельца (выше) и равенство чистых решений. Перевод ядра PR #38 на Go — после замера
на роутере и решения владельца.

## 4. Команда для владельца: прототип во /tmp, только чтение

Скачивает прототип с точного коммита, проверяет SHA-256, запускает `probe` (время узких и
полного чтений RCI и `ndmc show running-config`) и `dry-run` (план, который ядро ОТПРАВИЛО БЫ;
ничего не отправляет, файлов не пишет), печатает счётчики обращений к Keenetic за последние часы и
самые долгие ожидания, затем удаляет `/tmp/vward-core-proto`. Ничего на роутере не меняет.
Готовая команда с адресом коммита — в отчёте этой сессии и в `docs/AGENT.md` (запись 08.11).

## 5. Решение владельца по таблице (08.11, второе сообщение) — выполнено в PR #38

Все предложения §1 приняты; сделано настройками по умолчанию выпуска, код не удалён, каждое
можно включить обратно:

| Что | По умолчанию теперь | Включить обратно |
|---|---|---|
| policy-reconcile (00:10 и догоняющий запуск из обслуживания) | только наблюдение (`WOULD_REMOVE`) | `policy_reconcile=act` в `domain-lists.conf` (или `DRY_RUN=0`) |
| tunnel-health r6 (16 правил на OpkgTun4) | только наблюдение: расхождение раз за загрузку в журнал (`mismatch_observed`), ничего не отправляется | `dns_rules_check=1` (повтор как раньше); `0` — выключено |
| route-engine: перенос списков в туннель | только наблюдение (`LIST_AUTO_VPN_WOULD`) | `list_watch_act=1` |
| route-engine: привязки доменов к AdGuard в Keenetic и их снятие | только наблюдение (`AGH_BIND_WOULD`, `AGH_UNBIND_WOULD`) | `dns_bind_act=1` |
| сторож VPN | «Наблюдение» (агенты); при «Действии» — ≥3 мин молчания **по часам** (не по числу запусков) и событие sentinel «линк/адрес туннеля пропал»; иначе `WAIT_SENTINEL_CONFIRM` | `VWARD_GUARD_DOWN_CONFIRM` (не меньше 3) |
| сторож интернета | «Наблюдение» (агенты по умолчанию) | режим агента сети «Действие» |
| планировщик рекламы | раз в 5 минут; сторож DNS — своей ежеминутной строкой (`scheduler.sh dns`, те же проверки; его счёт «10 минут молчания» — минуты); `chain-fail` sentinel сразу запускает его проверку; задачи Панели — сразу после постановки | файл `/opt/etc/vward/ads-scheduler.every-minute` |
| сторож S91 | ежеминутная строка cron выключена (закомментирована); route-engine держит агент компонентов (проверка pid каждые 10 с, лимит 5 запусков в час, не во время обновления) | файл `/opt/etc/vward/route-engine.cron-watchdog` |
| проверка обновлений | неизменное состояние не переписывается (и без `sync`); отметка «лента ответила» — в RAM | — |

Установленные роутеры: установщик сохраняет crontab при обновлении, поэтому новые расписания
переносит обслуживание (housekeeping, ежечасно; копия crontab — в `backups/vward/cron-old`).

**Важное следствие правила сторожа VPN:** туннель, который молчит, но его линк не падает
(WireGuard/Xray-сервер умер, интерфейс поднят), sentinel не видит — сторож по нему не действует
(только `WAIT_SENTINEL_CONFIRM` в журнале). Так и задумано правилом «≥3 мин + событие sentinel».

**Шаг 2, сделано:** страницы (GET) отвечают из общей копии конфигурации, если она старше 55 с, но
моложе 5 мин, и тут же обновляют её в фоне (после любого изменения — только свежее чтение);
настройки, которые не читает маршрутизация (режим агентов, журналы, вход в Панель, канал
обновлений, автообновление компонентов, сторож интернета), берут свой короткий замок и не ждут до
10 с за изменением маршрутизации. **Дальше (после dry-run владельца):** узкие RCI вместо полного
`show running-config` в изменениях списков и в данных страниц (если `NARROW_EQUALS_FULL=true` на
5.1.8), файл состояния страниц, Go-ядро для смены сервисов.

## 6. Замер dry-run владельца (Viva, 08.11) и что сделано после него

Замер: полный `show running-config` — RCI 5,5 с, ndmc 12,7 с; узкое чтение 0,18 с (группы 133 мс,
dns-proxy 42 мс); `NARROW_EQUALS_FULL=true` для групп, маршрутов и строк Smart DNS; план 11 мс,
расчёт тумблера на 175 доменов 21 мс; RSS 4,9 МБ (dry-run). **Решение владельца: ядро
маршрутизации PR #38 переводится на Go; shell-ядро — откат до аппаратной приёмки.**

- **Узкие чтения в текущем коде** (главная причина «Роутер отвечает медленно»: 253 ожидания у
  сторожа DNS, 145 у route-engine, 48 у сверки маршрутов, 17 у качества туннелей, 12 у IP-категорий):
  `vward_keenetic_part groups|dnsproxy|nameservers|iproutes` выдаёт часть в виде строк
  running-config из поддерева RCI; первое использование в загрузке сверяется с полной
  конфигурацией, при расхождении (дважды) или отказе RCI — прежнее полное чтение до перезагрузки.
  Сторож DNS читает только `ip name-server` (строка цепочки AdGuard живёт там), route-engine —
  группы, dns-proxy и name-server, сверка — группы, качество туннелей — dns-proxy, IP-категории —
  все четыре части.
- **Владение для Go-ядра:** на роутере нет файлов `services/owned/*` (поэтому было `no-proof`).
  Ядро принимает те же доказательства, что shell: файл-подпись (полное владение), журнал
  завершённой транзакции создания группы (`service_origin`, полное), `managed.ГРУППА=1` (только
  маршрут списка). Остальное — чужое. Запись файлов-подписей (перенос) — при подключении ядра, по
  журналу; в dry-run видно, какой уровень получил каждый сервис и почему.
- **NextDNS:** ядро защищает его белым списком команд (только свои группы, маршруты своих и
  управляемых групп, свои строки Smart DNS; ничего с «next»), независимо от поиска; строки Smart
  DNS не пишутся без прочитанного `dns-proxy/filter`. Поиск исправлен: вся конфигурация и
  `GET dns-proxy/filter`. Тест на **реальной** форме ответа — после присланного вывода команды
  формы (в `docs/AGENT.md`); **до этого ядро не подключается**.
- **Порядок байтов без `od`** (в BusyBox Keenetic нет `-A`): sentinel, модули туннелей,
  официальная сборка AdGuard, команда dry-run.
- **Тумблер «Smart DNS»** (по умолчанию выключен): см. коммит `4dfbd73` и `check-smartdns-feature`.
- **Замер записи пачки** — не выполнялся; только по отдельному разрешению владельца.
